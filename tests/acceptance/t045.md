## Inventory

`POST /api/items` creates a fresh item in AVAILABLE; `GET /api/items/{itemId}`
inspects it. `POST /api/items/{itemId}/unavailable` changes an available item to
UNAVAILABLE. `POST /api/items/{itemId}/allocate` ordinarily produces ALLOCATED.
The intentionally inconsistent variant also permits that allocation after
UNAVAILABLE (200 / ALLOCATED). The repaired variant rejects it (409 /
UNAVAILABLE), retaining the unavailable state. Attempting to make an allocated
item unavailable is rejected in both variants.

Invariant: an item observed as UNAVAILABLE must not later be observed as
ALLOCATED within the same fresh trial, for the same item identity.

## Document workflow

`POST /api/documents` creates DRAFT; `GET /api/documents/{documentId}` inspects it.
`POST /api/documents/{documentId}/archive` produces ARCHIVED;
`POST /api/documents/{documentId}/publish` ordinarily produces PUBLISHED.
The intentionally inconsistent variant permits publication after archival
(200 / PUBLISHED). The repaired variant rejects it (409 / ARCHIVED), retaining
the archived state. Archiving a published document is rejected in both variants.

Invariant: a document observed as ARCHIVED must not later be observed as
PUBLISHED within the same fresh trial, for the same document identity.

Both predicates use existing JSON comparisons, identity equality and ordered
step-index applicability. No entity-specific engine evaluator or executable-code
predicate was added. Wrong entity/order is NOT APPLICABLE; missing evidence is
UNEVALUABLE. Guarded inconsistent transitions evaluate VIOLATED and their repaired
counterparts SATISFIED through the unchanged evaluator.

## Reset, inspection and authority

Both servers expose `POST /api/control/reset` returning `{ "reset": true }` and
`GET /api/control/baseline` returning the relevant collection count. Repeated
reset deterministically clears all relevant records; inspection reports zero.
Old identifiers become 404 and new trials create independently generated UUIDs.

Registry policies use the same contract as T035: RESET only in RESET; BASELINE
only in BASELINE; four journey operations in EXPLORATION, REPLAY, MINIMIZATION and
ARTIFACT. Tests reject cross-control phases, excluded operations, hallucinated
controls and forged journey phases. Actual supervisor tests reject forged-phase
and control intents during exploration without consuming additional budget or
creating a dispatched step. A rejected step is not resumed.

For both variants of each new fixture, full trials execute through existing
RunSupervisor → BudgetManager → frozen policy → cancellation → authoritative
executor. Independent exploration/replay each resets and verifies a SATISFIED
baseline before executing three journey steps. Trial IDs, baseline IDs and
response-produced entity IDs are distinct. The shared authoritative budget records
10 requests: RESET 2, BASELINE 2, EXPLORATION 3, REPLAY 3. Fixture servers only serve
requests; they have no outbound dispatcher or engine authority. Ordinary fixture
behavior tests use evaluator-only clients outside a GhostQA run, following T035.
